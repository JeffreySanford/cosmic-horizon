# Frontend Enhancements for Real‑Data Mode

The choice between using plain Promises or migrating the job-related
workflow to NgRx is orthogonal to these UI changes. In an NgRx-based setup
an effect can handle the HTTP call to `/jobs/submit` and another can poll
`/jobs/status`, with the store holding the `jobs` slice. All of the selectors
and component bindings shown below work equally well with or without a store.

To make the jobs interface aware of actual sky data and to expose the
capability of selecting or downloading real measurement sets, a few targeted
changes are required in the jobs console component and its template.

## UI changes

- **Dataset selector** – replace the static `datasetId` input with an
  autocomplete or dropdown populated from a manifest file (`assets/datasets.json`
  or generated by the backend). Keep the model a simple string or object; the
  component should **not** iterate the options on the `<input>` itself. Use
  reactive forms for clarity. Correct example:

  ```html
  <mat-form-field>
    <mat-label>Sky target</mat-label>
    <input
      matInput
      type="text"
      [formControl]="datasetControl"
      [matAutocomplete]="auto"
    />
    <mat-autocomplete #auto="matAutocomplete" [displayWith]="displayDataset">
      <mat-option *ngFor="let ds of datasets" [value]="ds">
        {{ ds.label }}
      </mat-option>
    </mat-autocomplete>
  </mat-form-field>
  ```

  ```ts
  datasetControl = new FormControl<DatasetEntry | null>(null);
  displayDataset(ds: DatasetEntry | null) { return ds?.label || ''; }
  ```

  This keeps the frontend decoupled from filesystem paths or container mounts.

- **Summary text** – include the chosen dataset, band, and a brief note from
  the manifest. The computed property now uses metadata extracted from the MS
  or the manifest.

  ```ts
  get scienceIntentSummary(): string {
    if (!this.selectedDataset) return '';
    const m = this.selectedDataset;
    return `${this.selectedAgent}: ${this.selectedAgentSummary.objective} on ${m.label} (${m.band})`;
  }
  ```

- **Progress/info panel** – when a CASA job completes, show a link to the FITS
  image or an embedded preview. This can reuse the existing `resultUrl` field
  returned by the API.

- **Fetch button** – optionally add a button labelled `Refresh datasets` that
  triggers the server endpoint to re‑scan `astronomy-data/` or run the download
  script; give feedback via a snackbar or spinner. That endpoint should also
  return the current free disk space, a `lastUpdated` timestamp, and a warning
  flag so the client can render a visible metric (e.g. "512 GB free – data last
  refreshed 2 days ago") and prevent the user from initiating a download if
  less than a configurable threshold (say 10 GB) is available. This ensures
  we don’t inadvertently try to download "nine petraflops" of data and blow the
  developer machine up.

- **Queue length & status** – display the current Redis queue depth (via
  `/queue/length`) and show a spinner or "waiting" badge when jobs are
  pending. This gives the user visibility into back-pressure and lets them
  decide whether to submit another job or wait.

- **Cancel control** – add a cancel button next to each running job; when
  clicked dispatch a `cancelJob` action (NgRx) or call `/jobs/cancel`. The
  effect should also handle the case where the job is already completed or
  failed.

- **Prometheus/Telemetry** – optionally display basic metrics collected from
  the backend (submitted, active, failed jobs) in a small dashboard tile or
  on the jobs console header.

- **Purge button** – provide a control labelled `Purge datasets` (perhaps in
  the same panel) that calls `DELETE /datasets/purge`. When pressed it
  removes all locally stored MS files, clears the manifest, and resets the
  `lastUpdated` indicator. Use a confirmation dialog and display the amount of
  space reclaimed, keeping the environment tidy.

The important point is that all of these enhancements piggy‑back on the
existing reactive form fields and HTTP clients; the rest of the UI behaviour
remains unchanged.

## Template example snippet

```html
<mat-form-field>
  <mat-label>Sky target</mat-label>
  <input
    type="text"
    matInput
    [matAutocomplete]="auto"
    [(ngModel)]="selectedDataset"
    [ngValue]="dataset"
    *ngFor="let dataset of datasets"
  />
  <mat-autocomplete #auto="matAutocomplete">
    <mat-option *ngFor="let ds of datasets" [value]="ds">
      {{ ds.label }}
    </mat-option>
  </mat-autocomplete>
</mat-form-field>
```

## Data flow

1. browser requests `/api/datasets`.
2. backend reads `astronomy-data/manifest.json` or examines the directory and
   returns metadata list.
3. user selects a dataset, which is included in the `submitJob()` payload.
4. API adapter (demo/LLM/CASA) receives the dataset id and can either ignore
   it (demo), feed it to the LLM prompt, or mount the corresponding MS in the
   processing container.

This design keeps the frontend decoupled from the actual file locations or
processing details – it only cares about a friendly identifier and some
metadata for display.
